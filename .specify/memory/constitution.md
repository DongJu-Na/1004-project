# PROJECT 1028 Constitution

## Core Principles

### I. 설계 문서 우선

- 기능은 두 갈래로 분류하며, 스펙 첫머리에 어느 갈래인지 명시한다 (MUST).
  - **게임 규칙 기능**: 의심(§2), NPC 유형(§3), 제압(§4), 신고(§5), 인카운터(§6),
    시간대 위협(§7), 코옵 규칙(§8) 등 플레이어 경험의 규칙을 정하는 기능.
  - **기반 기능**: 이동·카메라·상호작용·NPC 뼈대·대화 표시·차량·저장·타이틀·옵션 메뉴 등
    게임 규칙을 담는 그릇이 되는 기능. 그 자체로 새로운 게임 규칙을 도입하지 않는다.
- 게임 규칙 기능은 루트 `spec.md`(Story & System Design Document, 현재 v0.8)의 `확정`
  표기 조항을 근거로만 구현한다 (MUST).
- 기반 기능은 `Docs/PrototypePlan.md` 또는 선행 SDD v0.4~v0.7의 조항을 근거로 구현할 수
  있다 (MAY). 기반 기능 스펙은 "기반 기능"임을 표시하고, 게임 규칙 요소(의심 수치, 진영
  판정, 위협 반응 등)를 포함하지 않음을 선언한다 (MUST). 기반 기능에 게임 규칙이 섞이면
  해당 부분은 게임 규칙 기능으로 분리하여 SDD `확정` 근거를 갖춘다.
- `[제안]` 표기 조항은 SDD에서 `확정`으로 전환되기 전에는 구현하지 않는다 (MUST NOT).
  튜닝 수치·목록·대본 등 `[제안]` 상태인 값은 스펙과 태스크에 "확정 대기"로 명시한다.
- 스펙(`specs/*/spec.md`)의 모든 요구사항은 근거 조항을 인용한다 (MUST). 게임 규칙 기능은
  SDD 조항 번호(예: §2.5, §4.2), 기반 기능은 PrototypePlan 단계 번호(예: PrototypePlan 1단계)
  또는 선행 SDD 버전·조항(예: v0.6 §3.1)을 쓴다. 근거가 없는 요구사항은 해당 문서의 개정을
  먼저 요청한다.
- 근거: SDD는 v0.1부터 v0.8까지 결정을 누적한 유일한 진실 원천이다. 근거 없는 구현은
  나중 버전에서 모순을 만들고, `[제안]` 항목은 아직 팀이 합의하지 않은 값이다. 한편 v0.8은
  게임성 규격만 다루므로, 그 규격을 검증하려면 먼저 있어야 하는 이동·NPC·대화 같은
  기반은 프로토타입 계획과 선행 SDD를 근거로 삼는 것이 현실적이다.

### II. 에셋 예산 준수

- 신규 에셋(모델, 텍스처, 사운드, 애니메이션 등)은 "에셋 예산 v0.1" 범위 안에서만
  계획한다 (MUST).
- 예산 범위를 넘는 신규 에셋은 `/speckit-specify` 단계에서 스펙 문서에 항목·수량·초과
  사유를 명시하고, 명시적 승인을 받기 전에는 plan/tasks로 진행하지 않는다 (MUST).
- 인카운터 제작 단가(SDD §6.1)는 예산의 일부로 취급한다. 인카운터를 추가하는 스펙은
  단가 합계를 기재한다 (MUST).
- 근거: 소규모 팀 프로젝트에서 에셋 범위 초과는 가장 흔한 일정 붕괴 원인이다. 예산은
  스펙 단계에서만 저렴하게 조정할 수 있다.

### III. 시스템 단위 독립 테스트

- 의심 시스템(SDD §2), 제압 시스템(§4), 인카운터 시스템(§6)은 각각 다른 시스템 없이
  단독으로 검증 가능해야 한다 (MUST).
- 각 시스템은 입력·상태·출력이 명확한 경계를 가지며, 다른 시스템과의 결합은 명시된
  인터페이스(이벤트 또는 데이터 계약)로만 이루어진다 (MUST).
- 시스템별 검증은 실제 맵·NPC·에셋 없이 실행 가능한 테스트 씬 또는 단위 테스트로
  제공한다 (MUST). 시스템 간 상호작용(예: 제압 → 섬 의심도 상승)은 별도의 통합 테스트로
  다룬다.
- 근거: 세 시스템은 SDD에서 서로 다른 장에 독립적으로 규격화되었고, 수치 튜닝(§2.3,
  §6.3)이 반복될 예정이다. 독립 검증 없이는 튜닝 결과를 시스템별로 귀속시킬 수 없다.

### IV. 코옵 호환

- 모든 게임 규칙은 싱글 플레이와 코옵에서 동일하게 동작해야 한다 (MUST). 플레이어 수에
  따라 규칙 자체가 달라지는 분기를 두지 않는다 (MUST NOT).
- SDD §8의 공유 규칙을 깨지 않는다 (MUST): 개인 의심은 플레이어별 개별 값, 섬 의심도는
  팀 전체 공유 값이다.
- 제압·운반 등 손 제약(§4.2, §8.3)은 코옵에서도 플레이어별로 동일하게 적용한다 (MUST).
- 새 스펙은 "싱글에서의 동작"과 "코옵에서의 동작"을 각각 한 문장 이상으로 기술하고,
  차이가 없음을 확인한다 (MUST).
- 근거: 코옵은 SDD v0.6에서 정당성을 확보한 핵심 기능이며, "한 명의 실수가 전원에게
  돌아온다"(§8.1)는 긴장 설계의 근간이다. 싱글 전용 로직은 이 구조를 조용히 무너뜨린다.

### V. 폐기 항목 부활 금지

- SDD §10에서 폐기된 항목(권총, 산탄총, 근접 무기 등 살상·호신용 무기)은 어떤 형태로도
  스펙·플랜·태스크·코드에 재도입하지 않는다 (MUST NOT).
- 폐기 항목을 재도입하려면 먼저 이 헌장의 개정(MAJOR 버전 상승)과 SDD §10의 개정이
  모두 선행되어야 한다 (MUST).
- 위협에 대한 플레이어의 물리적 대응은 제압(비살상, §4)만 허용한다 (MUST).
- 근거: "폭력은 해결책이 아니라 지연책이다"(§1 원칙 4)는 이 게임을 호러·서바이벌
  장르와 구분하는 핵심 결정이다. 무기 재도입은 장르 자체를 바꾸는 결정이므로 헌장 수준의
  합의를 요구한다.

## 근거 문서 및 상태 표기

- 진실 원천 우선순위: (1) 이 헌장 → (2) 루트 `spec.md` SDD 최신 버전 → (3) 선행 SDD
  v0.4~v0.7 및 에셋 예산 v0.1 → (4) `Docs/PrototypePlan.md` → (5) `specs/NNN-*/` 산출물 →
  (6) 코드. 상위 문서와 하위 문서가 충돌하면 상위 문서가 우선한다.
- 기반 기능 근거(원칙 I): `Docs/PrototypePlan.md`는 기반 기능의 범위와 완료 기준을 정한다.
  PrototypePlan이 "범위 밖"으로 명시한 항목(전투, 다수 NPC 스케줄, 래그돌, 온라인, 실제 섬
  규모 맵, 복수 차량, 최종 아트·사운드)은 기반 기능 스펙에 포함하지 않는다 (MUST NOT).
  단, SDD `확정` 조항이 요구하는 경우 게임 규칙 기능으로 별도 스펙을 만든다.
- 선행 SDD v0.4~v0.7은 현재 저장소에 없다. 기반 기능이 이를 인용할 때는 조항 원문을 스펙에
  발췌하여 검토자가 저장소 안에서 확인할 수 있게 한다 (MUST).
- 루트 `spec.md`는 spec-kit 산출물이 아니다. `/speckit-*` 명령은 이 파일을 읽기 전용
  입력으로만 사용하며 덮어쓰지 않는다 (MUST NOT). 기능별 스펙은 `specs/NNN-이름/spec.md`에
  생성한다.
- SDD 상태 표기 해석: `확정` = 구현 가능, `[제안]` = 확정 대기(원칙 I), 폐기(§10) =
  재도입 금지(원칙 V).
- 참조 문서 위치: 에셋 예산 v0.1은 현재 저장소에 없다. 원칙 II 판정 시 문서 위치를
  스펙에 기재한다.

## 개발 워크플로우 및 품질 게이트

- 기능 개발 순서는 `/speckit-specify` → `/speckit-clarify`(필요 시) → `/speckit-plan` →
  `/speckit-tasks` → `/speckit-implement`를 따른다 (MUST). 순서를 건너뛰어 코드부터
  작성하지 않는다.
- Specify 게이트: 스펙 첫머리에 게임 규칙/기반 기능 분류가 있고(원칙 I), 각 요구사항에
  분류에 맞는 근거 조항이 있으며(원칙 I), `[제안]` 의존 항목이 "확정 대기"로 표시되어
  있고(원칙 I), 신규 에셋 목록과 예산 초과 여부가
  기재되어 있고(원칙 II), 싱글·코옵 동작이 각각 기술되어 있어야(원칙 IV) 통과한다.
- Plan 게이트: 플랜의 Constitution Check 섹션에서 원칙 I~V를 각각 판정한다 (MUST).
  하나라도 위반이면 Complexity Tracking에 사유를 적거나 스펙으로 되돌린다.
- Tasks 게이트: 시스템별 독립 테스트 태스크가 구현 태스크보다 앞서 배치되어야 한다
  (원칙 III).
- Implement 게이트: 폐기 항목(원칙 V)에 해당하는 식별자·에셋·로직이 코드에 없어야 한다.
  `/speckit-analyze`로 spec·plan·tasks 간 일관성을 확인한 뒤 구현한다 (SHOULD).
- 이 저장소는 현재 git 관리 대상이 아니다. 헌장 개정과 스펙 산출물 변경은 문서 안의
  버전·날짜 표기로 이력을 남긴다 (MUST).

## Governance

- 이 헌장은 이 프로젝트의 다른 모든 개발 관행과 산출물 템플릿보다 우선한다.
- 개정 절차: (1) 변경 사유와 영향 범위를 문서화 → (2) `/speckit-constitution`으로 초안
  작성 → (3) 프로젝트 책임자 승인 → (4) 영향받는 `specs/*` 산출물에 전파. 원칙 V 관련
  개정은 SDD §10 개정을 반드시 동반한다.
- 버전 정책(시맨틱 버저닝): MAJOR = 원칙 삭제·재정의 또는 하위 호환 불가 변경, MINOR =
  원칙·섹션 추가 또는 실질적 확장, PATCH = 문구·오타·명확화.
- 준수 검토: 모든 `/speckit-plan` 실행은 Constitution Check에서 원칙 I~V를 판정한다.
  `/speckit-analyze`는 헌장 위반을 CRITICAL로 보고한다. 위반이 확인되면 구현을 중단하고
  스펙 또는 헌장 개정으로 해소한다.
- 런타임 개발 지침은 `.claude/skills/speckit-*/SKILL.md`와 `.specify/templates/`를 따른다.
