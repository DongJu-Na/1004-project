# Feature Specification: 인카운터 프레임워크 (Encounter Framework)

**Feature Branch**: `007-encounter-framework`

**Created**: 2026-09-23

**Status**: Draft

**Input**: User description: "게임 규칙 기능. SDD §6(확정)의 시스템 부분을 구현한다. 인카운터의 구성 단위(§6.1 트리거+NPC 1~2+대사 3~5줄+결과 플래그), 네 유형의 결과 계약(§6.2), 스폰 규격(§6.4), 회수 테이블의 형식과 플래그 저장(§6.5)을 포함한다. 유형 비율(§6.3)은 [제안]이므로 데이터 값으로 분리하고 확정 대기. 개별 인카운터 20~30개 목록과 회수 테이블 내용은 v0.9 예정이므로 범위 밖이며, 검증용 샘플만 둔다. 001의 대화 표시, 006의 차량 상태, 002의 시간대·섬 의심도를 사용한다. 신규 에셋 없음(§6.1). 싱글·코옵 동작 차이 없음. 테스트 씬에서 단독 검증 가능해야 한다."

## Constitution Compliance *(constitution v1.1.0)*

- **기능 분류 (원칙 I)**: **게임 규칙 기능**.
- **근거 조항 (원칙 I)**: SDD v0.8 §6 인카운터 시스템 `확정`(§6.1 제작 단가, §6.2 네 유형, §6.4 스폰 규격,
  §6.5 회수), §7 시간대 `확정`(시간대 조건), §2.4 구간 `확정`(진행도 조건의 일부로 섬 의심도 구간 사용).
- **확정 대기 항목 (원칙 I)**: §6.3 유형 비율은 `[제안]`이므로 데이터 파일 값으로 분리하고 `확정 대기`. §9
  "인카운터 20~30개 개별 목록 — v0.9", "회수 테이블 전체 — v0.9"는 범위 밖이다. 이 스펙의 샘플 인카운터는
  검증용이며 게임 콘텐츠가 아님을 데이터에 표시한다. §6.2 B "주민이 쳐다본다 → 지나가면 의심 +1", C "태운다 →
  섬 의심도 급등"의 수치는 002의 상승 표(확정 대기)를 통해 적용한다.
- **의존성**: 001(대화 표시·이동 상태), 002(시간대·섬 의심도·상승 사건), 006(차량 이동 중 여부). 003~005는
  선택 의존(샘플 인카운터가 NPC 유형·제압을 쓸 수 있으나 프레임워크 검증에는 불필요).
- **다른 시스템으로 넘기는 것**: 회수의 실제 발동(다음 섬에서 증언, 장부의 취소선 등)은 v0.9 콘텐츠와 문서·
  증거 시스템이 맡는다. 이 스펙은 결과 플래그를 기록하고 회수 테이블 형식으로 조회 가능하게 하는 데서 끝난다.
  플래그의 런 간 보존은 저장 기능(PrototypePlan 5단계)이 맡는다.
- **신규 에셋 (원칙 II)**: 없음. §6.1 "기존 에셋만 사용(신규 제작 0)"이 이 시스템의 정의다. 샘플 인카운터의
  NPC·물건은 001~006의 프리미티브다. 인카운터 추가 스펙은 단가 합계(트리거·NPC 수·대사 줄 수)를 기재해야
  한다(헌장 원칙 II).
- **독립 검증 (원칙 III)**: 테스트 씬에 이동 경로(도로) 1개, 차량 1대, 샘플 인카운터 8개(유형별 2개), 플레이어
  1~2개. 시간대·섬 의심도는 002의 스위치로 조작한다.
- **싱글·코옵 동작 (원칙 IV)**: 인카운터는 씬(런) 단위로 발생하며 모든 플레이어에게 같은 사건이다. 트리거는
  "어느 플레이어든 조건을 만족하면" 발동하고, 선택형(C)의 선택은 먼저 선택한 플레이어의 것이 적용된다. 결과
  플래그는 런 공유 값이다. 싱글은 플레이어가 1명인 특수 경우다.
- **폐기 항목 (원칙 V)**: 인카운터 결과에 무기 획득·살상 대응은 없다. "누군가 맞고 있다 → 개입하면 §4의 대가"는
  004의 비살상 제압을 호출한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 이동 중에 인카운터가 뜨고, 대화하고, 플래그가 남는다 (Priority: P1)

플레이어가 도로를 따라 이동하는 동안 조건을 만족한 인카운터가 발생한다. NPC 1~2명이 등장하고 3~5줄의
대화가 표시되며, 끝나면 결과 플래그가 런에 기록된다. §6.1 §6.4

**Why this priority**: 인카운터의 최소 단위다. 이것이 있어야 유형·스폰 규칙·회수를 얹을 수 있다.

**Independent Test**: 인카운터 1개를 "항상 발생"으로 설정하고 도로를 걸어 트리거 → NPC 등장 → 대화 → 플래그
기록을 확인한다.

**Acceptance Scenarios**:

1. **Given** 플레이어가 도로 위에서 이동 중이고 인카운터 조건이 충족된다, **When** 트리거 지점을 지난다,
   **Then** 인카운터의 NPC가 등장하고 첫 대사가 001의 대화 표시로 나온다.
2. **Given** 대화가 진행 중이다, **When** 마지막 줄이 끝난다, **Then** 인카운터가 종료되고 데이터에 정의된
   결과 플래그가 런 기록에 남는다.
3. **Given** 인카운터 데이터의 대사가 3~5줄이 아니다, **When** 로드한다, **Then** 테스트 씬에 "§6.1 규격 위반"
   경고가 남고 게임은 멈추지 않는다.
4. **Given** 인카운터 데이터의 NPC 수가 0 또는 3 이상이다, **When** 로드한다, **Then** 같은 방식으로 경고를 남긴다.

### User Story 2 - 네 유형은 결과 계약이 다르다 (Priority: P1)

기회형(A)은 정보·증거·신뢰 같은 이득 플래그를, 위협형(B)은 위험 사건(의심 상승 등)을, 도덕적 선택형(C)은
플레이어의 선택 하나와 선택별 결과를, 세계 채색형(D)은 아무 결과 없음을 낸다. D는 반드시 섞여 있어야 한다.
§6.2

**Why this priority**: "전부 결과가 있으면 플레이어가 인카운터를 회피한다"(§6.2 D). 유형 계약이 프레임워크의
핵심 설계다.

**Independent Test**: 유형별 샘플 2개씩을 발생시켜 결과 계약이 유형에 맞는지, D는 플래그·수치 변화가 0인지
확인한다.

**Acceptance Scenarios**:

1. **Given** A 유형 인카운터가 끝났다, **When** 결과를 본다, **Then** 이득 플래그(예: 정보 획득) 1개 이상이
   기록되고 의심 값은 오르지 않는다.
2. **Given** B 유형 인카운터가 진행된다, **When** 정의된 위험 조건(예: 시야 안 통과)이 충족된다, **Then**
   002의 상승 사건이 발생한다(값은 상승 표, 확정 대기).
3. **Given** C 유형 인카운터가 진행된다, **When** 대화 중 선택지가 제시된다, **Then** 플레이어는 두 가지 중
   하나를 골라야 하고, 선택별로 다른 결과 플래그와 사건이 적용된다. 선택 전에는 대화가 진행되지 않는다.
4. **Given** D 유형 인카운터가 끝났다, **When** 결과를 본다, **Then** 결과 플래그 0개, 의심 변화 0, 단 "발생
   이력"은 남는다(재등장 금지용).
5. **Given** 풀에 D 유형이 하나도 없다, **When** 로드한다, **Then** "D 유형 필수" 경고가 남는다.

### User Story 3 - 너무 자주, 연속으로, 같은 것이 뜨지 않는다 (Priority: P2)

인카운터는 이동 중에만, 런당 2~4개, 최소 간격을 두고, 차량 이동 중에는 도보보다 높은 확률로 발생한다.
섬 전용 풀과 공용 풀에서 고르고, 시간대·진행도 조건을 따르며, 같은 인카운터는 변주 없이 다시 나오지 않는다.
§6.4

**Why this priority**: "섬이 작다. 너무 자주 뜨면 억지스럽다." 스폰 규격이 체감 품질을 결정한다.

**Independent Test**: 런을 20회 시뮬레이션해 발생 수·간격·중복·시간대 조건 위반을 집계한다.

**Acceptance Scenarios**:

1. **Given** 플레이어가 조사·정찰 상태(외부 입력) 또는 대화 중이다, **When** 트리거 지점을 지난다, **Then**
   인카운터가 발생하지 않는다.
2. **Given** 런에서 이미 4개가 발생했다, **When** 조건을 충족하는 트리거를 지난다, **Then** 발생하지 않는다.
3. **Given** 직전 인카운터가 최소 간격 안에 끝났다, **When** 다음 트리거를 지난다, **Then** 발생하지 않는다.
4. **Given** 같은 트리거를 도보와 차량으로 각 100회 지난다, **When** 발생 횟수를 비교한다, **Then** 차량 쪽이
   더 많다(확률은 데이터 파일).
5. **Given** 인카운터에 "밤 전용" 조건이 있다, **When** 시간대가 낮이다, **Then** 후보에서 제외된다.
6. **Given** 인카운터에 "섬 의심도 경계 이상" 조건이 있다, **When** 구간이 평온이다, **Then** 후보에서 제외된다.
7. **Given** 인카운터 X가 이 런 또는 이전 런에서 발생했다(이력 입력), **When** 후보를 고른다, **Then** X의 원본은
   제외되고, X의 변주가 정의되어 있으면 변주만 후보가 된다.
8. **Given** 현재 섬 전용 풀과 공용 풀이 있다, **When** 후보를 고른다, **Then** 두 풀에서 모두 고를 수 있고 다른 섬
   전용 풀은 제외된다.

---

### User Story 4 - 결과가 나중에 돌아온다: 회수 테이블 (Priority: P2)

인카운터의 결과 플래그는 회수 테이블에서 "어떤 플래그가 → 어디서 → 무엇을 바꾸는가"로 조회된다. 이 스펙은
테이블의 형식과 조회를 제공하고, 샘플 회수 1~2개로 동작을 검증한다. 실제 회수 내용은 v0.9다. §6.5

**Why this priority**: "나중에 다시 나타나기 때문에 기억에 남는다." 형식을 지금 정하지 않으면 v0.9에서 플래그
설계를 다시 해야 한다.

**Independent Test**: C 유형 샘플에서 "태우지 않았다" 플래그를 남기고, 회수 테이블 조회로 후속 인카운터 변주가
후보에 들어오는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 런에 플래그 F가 기록됐다, **When** 회수 테이블을 F로 조회한다, **Then** F를 조건으로 갖는 회수
   항목(대상: 후속 인카운터 변주·문서 변화·NPC 대사 변화 중 하나)이 반환된다.
2. **Given** 회수 항목이 "후속 인카운터 변주"다, **When** 다음 스폰 후보를 고른다, **Then** 그 변주가 후보에
   포함된다.
3. **Given** 회수 항목이 "문서 변화"(예: 장부 취소선)다, **When** 조회한다, **Then** 이 스펙은 항목을 반환만
   하고 실제 문서 변화는 일으키지 않는다(문서 시스템 범위 밖).
4. **Given** 런이 끝났다, **When** 플래그 목록을 조회한다, **Then** 이 런의 모든 결과 플래그와 발생 이력이
   외부(저장 기능)로 넘길 수 있는 형태로 노출된다.

---

### Edge Cases

- 트리거 지점을 두 플레이어가 거의 동시에 지나면: 한 번만 발생한다.
- 인카운터 진행 중 다른 트리거를 지나면: 무시된다.
- 인카운터 NPC가 대화 도중 제압되면(004): 인카운터는 "중단"으로 끝나고 결과 플래그는 기록되지 않으며 §4.4
  대가는 그대로 적용된다.
- C 유형 선택 중 플레이어가 자리를 떠나면(차량으로 지나감): "선택하지 않음"으로 처리되고 데이터에 정의된 기본
  결과가 적용된다.
- 런당 상한이 2 미만으로 설정되면: 데이터 오류로 경고하고 2로 취급한다.
- 풀이 비어 있으면: 인카운터가 발생하지 않고 경고를 남긴다.
- 인카운터 NPC 등장 위치가 막혀 있으면: 대체 위치를 쓰거나 이번 트리거를 건너뛴다.
- 변주가 없는 인카운터를 모두 소진하면: 남은 런 동안 더 발생하지 않는다(억지 반복 금지).

## Requirements *(mandatory)*

### Functional Requirements

**구성 단위** §6.1

- **FR-001**: 인카운터는 씬 밖 데이터로 정의되어야 하며 (식별자, 유형 A/B/C/D, 트리거 조건, NPC 1~2명 정의,
  대사 3~5줄, 결과 계약, 스폰 조건, 소속 풀, 변주 관계)를 가져야 한다.
- **FR-002**: NPC 수 1~2, 대사 3~5줄 규격을 벗어나면 게임을 멈추지 않고 경고를 남겨야 한다.
- **FR-003**: 인카운터는 신규 에셋을 요구하지 않아야 한다. 데이터가 참조하는 NPC·물건은 기존 것이어야 한다.
- **FR-004**: 검증용 샘플 인카운터는 데이터에 "샘플(콘텐츠 아님)" 표시를 가져야 한다.

**네 유형의 결과 계약** §6.2

- **FR-005**: A 기회형은 종료 시 이득 플래그 1개 이상을 기록해야 하고 의심 상승 사건을 내지 않아야 한다.
- **FR-006**: B 위협형은 정의된 위험 조건 충족 시 002의 상승 사건을 발생시켜야 한다. 값은 002 상승 표(확정 대기).
- **FR-007**: C 도덕적 선택형은 대화 중 정확히 하나의 이지선다를 제시해야 하고, 선택 전에는 진행되지 않으며,
  선택별로 결과 플래그·사건이 달라야 한다. 이탈 시 기본 결과가 적용된다.
- **FR-008**: D 세계 채색형은 결과 플래그·의심 변화·사건이 없어야 하며 발생 이력만 남긴다.
- **FR-009**: 풀에 D 유형이 하나도 없으면 경고를 남겨야 한다.
- **FR-010**: 유형 비율은 데이터 파일 값이며 `확정 대기`로 표시된다. §6.3 제안값(30/25/20/25)은 초깃값이다.
  스폰 선택은 이 비율을 가중치로 써야 한다.

**스폰 규격** §6.4

- **FR-011**: 인카운터는 플레이어가 "이동 중"(001 도보 이동 또는 006 차량 이동)이고 대화·조사·정찰 상태가
  아닐 때만 발생해야 한다. 조사·정찰 상태는 외부 불리언 입력이다.
- **FR-012**: 런당 발생 수는 데이터 파일의 하한·상한(초깃값 2~4) 안이어야 한다.
- **FR-013**: 연속 발생 사이에 데이터 파일의 최소 간격(시간 또는 거리)이 있어야 한다.
- **FR-014**: 차량 이동 중 발생 확률은 도보보다 높아야 한다. 두 확률은 데이터 파일 값.
- **FR-015**: 후보는 현재 섬 전용 풀과 전 섬 공용 풀에서 골라야 하며 다른 섬 전용 풀은 제외한다.
- **FR-016**: 인카운터는 시간대 조건(낮·밤·무관)과 진행도 조건(섬 의심도 구간, 특정 플래그 보유 여부)을 가질
  수 있어야 하고, 불충족 시 후보에서 제외되어야 한다.
- **FR-017**: 이미 발생한 인카운터(이 런 + 이력 입력)의 원본은 후보에서 제외되어야 한다. 변주가 정의되어 있으면
  변주만 후보다.
- **FR-018**: 진행 중인 인카운터가 있으면 새 트리거는 무시되어야 한다.

**결과 플래그와 회수** §6.5

- **FR-019**: 결과 플래그는 런 단위로 기록되고 모든 플레이어가 공유해야 한다.
- **FR-020**: 회수 테이블은 씬 밖 데이터로 (조건 플래그, 회수 대상 종류: 후속 인카운터 변주·문서 변화·NPC 대사
  변화, 대상 식별자, 설명)을 가져야 하며 플래그로 조회 가능해야 한다.
- **FR-021**: 회수 대상이 "후속 인카운터 변주"이면 그 변주가 스폰 후보에 포함되어야 한다. 그 외 종류는 반환만
  하고 실행은 해당 시스템에 맡긴다.
- **FR-022**: 런 종료 시 결과 플래그와 발생 이력을 외부에 넘길 수 있어야 한다(저장은 후속).
- **FR-023**: 인카운터가 중단되면(NPC 제압 등) 결과 플래그는 기록되지 않고 발생 이력만 남아야 한다.

**노출·검증** (원칙 III)

- **FR-024**: 테스트 씬에서 현재 후보 목록·발생 수·다음 가능 시점·기록된 플래그·발생 이력을 확인할 수 있어야 한다.
- **FR-025**: 테스트 씬에서 특정 인카운터를 강제 발생시키고, 런을 자동 반복 시뮬레이션할 수 있어야 한다.

### Key Entities

- **인카운터 정의**: 식별자, 유형, 트리거, NPC 1~2, 대사 3~5줄, 결과 계약, 스폰 조건(시간대·진행도), 풀, 변주 관계,
  샘플 표시.
- **인카운터 인스턴스**: 진행 상태(대기·진행·종료·중단), 등장 NPC, 선택 결과.
- **결과 플래그**: 이름, 기록 시각, 출처 인카운터. 런 공유.
- **발생 이력**: 이 런과 이전 런에서 발생한 인카운터 식별자 집합.
- **풀**: 섬 전용 또는 공용. 인카운터 식별자 목록.
- **회수 항목**: 조건 플래그, 대상 종류, 대상 식별자, 설명.
- **스폰 상태**: 런 발생 수, 마지막 발생 시점·위치, 현재 이동 수단.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 런 자동 시뮬레이션 100회에서 발생 수가 모두 2~4 안이고, 최소 간격 위반 0회, 원본 중복 0회.
- **SC-002**: 같은 트리거를 도보·차량으로 각 100회 통과 시 차량 발생 수가 도보보다 많다.
- **SC-003**: 유형별 샘플 8개에서 결과 계약 위반 0회(A 이득만, B 상승 사건, C 선택 강제, D 무결과).
- **SC-004**: 시간대·진행도 조건이 걸린 샘플이 조건 불충족 시 100회 시뮬레이션에서 0회 발생한다.
- **SC-005**: C 샘플의 두 선택이 각각 다른 플래그를 남기고, 회수 조회로 후속 변주가 후보에 들어오는 것을 10회 중
  10회 확인한다.
- **SC-006**: 조사·정찰·대화 상태에서 트리거 100회 통과 시 발생 0회.
- **SC-007**: 신규 에셋 0개. 샘플 8개의 단가 합계(NPC 수·대사 줄 수)가 데이터에 기재되어 있다.

## Assumptions

- **"이동 중"**: 001의 도보 이동 상태 또는 006의 차량 이동 중. "조사·정찰 중"은 후속 증거 시스템이 제공할 상태이므로
  외부 불리언 입력으로 받는다.
- **트리거**: 도로 위 지점 통과를 기본 트리거로 한다. 시간 기반·확률 기반 트리거도 데이터로 정의할 수 있다.
- **"섬"**: 아직 섬이 하나뿐이므로 풀은 "현재 섬 전용 1개 + 공용 1개"로 검증한다. 섬 식별자는 외부 입력.
- **C 유형의 "태운다"**: 006의 동승석에 NPC를 앉히는 동작이 필요하다. 이 스펙의 샘플은 "선택 → 플래그"까지만
  검증하고, NPC 탑승 연출은 v0.9 콘텐츠 스펙에서 006을 확장한다.
- **B 유형 검문**: 샘플은 "경비 시야 안 통과 시 상승 사건"으로 단순화한다. 차량 정지 강제·증거 검사는 증거
  시스템 이후다.
- **회수 테이블 내용**: §6.5 표의 3항목(태워준 노동자·정비공·안 태운 사람)은 형식 검증용 샘플로만 넣고 "샘플" 표시.
- **이전 런 이력**: 저장이 없으므로 테스트 씬에서 수동 입력한다.
- **의존성**: 001, 002, 006 완료. 003~005는 선택.
